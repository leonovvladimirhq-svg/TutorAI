# CLOUD.md — TutorAI в облаке

Документ описывает, **что это за проект, как он устроен, какая облачная инфраструктура
нужна и как его развернуть** в Yandex Cloud. Читается «с нуля» — без знания истории разработки.

---

## 1. Что это и зачем

**TutorAI («Наставник AI»)** — Telegram-бот, персональный ИИ-наставник студента для ОП
«Интегрированные коммуникации» ШК ВШЭ. Помогает студенту:

- собрать **учебно-карьерный профиль** в коучинговом диалоге (текст или голос);
- сформулировать **цели по методике SMART**;
- видеть и редактировать свой профиль;
- (в дальнейшем) получать напоминания о дедлайнах, рекомендации курсов, аналитику для наставника.

Зачем: на курсе 2 наставника на ~75 студентов — глубокой персональной работы на всех не хватает.
Бот берёт на себя рутину (профайлинг, постановка целей, аналитика), не заменяя наставника.
Бот — `@tutor_hse_ai_bot`. Это прототип; цель — рабочая, расширяемая архитектура.

---

## 2. Архитектура

```
Студент ──Telegram (текст/голос)──► Бот (aiogram, long-polling)
                                       │
                  ┌────────────────────┼─────────────────────┐
                  ▼                    ▼                     ▼
            PostgreSQL          Yandex AI Studio        Yandex SpeechKit
        (профиль, цели,          (Qwen — диалог,          (распознавание
         история, события)        извлечение фактов,       голоса → текст)
                                   SMART-цели)
```

- **Канал** — Telegram (long-polling, домен/webhook не нужны).
- **Ядро** — структурированный профиль студента с провенансом (у каждого факта — источник
  и статус подтверждения). В профиль попадает только то, что студент подтвердил.
- **LLM** — Qwen в Yandex AI Studio (OpenAI-совместимый API, авторизация IAM-токеном).
- **STT** — Yandex SpeechKit (OggOpus из Telegram → текст).
- **Хранилище** — PostgreSQL (в прототипе — контейнер; для прода можно Managed PostgreSQL).
- **Метрики** — таблица событий + команда `/stats` (доля SMART-целей, заполненность профиля,
  вовлечённость).

Подробнее о коде — в [README.md](README.md).

## 4. Облачная инфраструктура (Yandex Cloud)

Что используется в каталоге Yandex Cloud:

1. **AI Studio** — инференс модели Qwen (Qwen3 30B-A3B). Оплата по токенам.
2. **SpeechKit** — распознавание речи. Оплата по секундам аудио.
3. **Compute Cloud (VM)** — одна виртуальная машина, на которой в Docker работают бот и Postgres.
4. (Опционально для прода) **Managed PostgreSQL** вместо контейнера.

GPU не нужен: модель крутится в AI Studio, на VM — только лёгкие бот и БД.

### 4.1. Конфигурация VM и стоимость

Рекомендуемая (экономичная) конфигурация:

| Параметр | Значение | Зачем |
|----------|----------|-------|
| Платформа | standard-v3 | актуальная серия |
| vCPU | 2 ядра, **гарантированная доля 50%** | бот почти всё время простаивает → платим вдвое меньше за vCPU |
| RAM | 4 ГБ | хватает боту + Postgres (лимит заказчика — ≤6 ГБ) |
| Диск | network-HDD, 20 ГБ | дешевле SSD, для прототипа достаточно |
| ОС | Ubuntu 22.04 LTS | |
| Прерываемая | нет | бот должен работать постоянно |
| Публичный IP | да (NAT) | для исходящих запросов и polling |

**Оценка стоимости:** такая VM на on-demand ориентировочно укладывается в **~1000–1500 ₽/мес**,
что ниже целевого потолка (1500–2000 ₽/мес). Точную сумму даёт
[калькулятор Yandex Cloud](https://yandex.cloud/ru/prices). Снизить ещё:

- **Committed-use (резервирование ресурсов на срок)** — скидка за обязательство, как раз тот
  механизм «гарантированного резервирования», о котором речь: при коммите на 1–3 мес/года
  стоимость VM падает ощутимо.
- **network-HDD** вместо SSD (уже учтено).
- Инференс AI Studio и SpeechKit оплачиваются отдельно по факту; на объёме пилота
  (десятки студентов) это малые суммы.

Сервисный аккаунт `leonov-deployer` (`ajercun172vma0sg1eig`) аутентифицируется, видит организацию
`organization-ihorrible01` (`bpfq22e6d6hr0oaelniq`), но **не видит ни одного облака/каталога** —
значит, прав на уровне облака у него нет. Нужно одно из двух:

**Минимум — просто сообщить ID каталога «наставник AI»** (в консоли Yandex Cloud: каталог →
поле «Идентификатор», вид `b1gxxxxxxxxxxxxxxxxx`). Тогда я подключусь напрямую.

**И обязательно — выдать сервисному аккаунту роли на каталоге «наставник AI»:**

| Роль | Для чего |
|------|----------|
| `ai.languageModels.user` | вызовы Qwen (AI Studio) |
| `ai.speechkitStt.user` | распознавание речи (голосовой ввод) |
| `compute.editor` | создание и управление виртуальной машиной |
| `vpc.user` | сеть/подсеть для VM |
| `resource-manager.viewer` (желательно, на облако/каталог) | чтобы инструменты могли находить каталог по имени |

Как выдать (в консоли: каталог «наставник AI» → «Права доступа» → «Назначить роли» →
сервисный аккаунт `leonov-deployer`), либо командой:

```bash
yc resource-manager folder add-access-binding <FOLDER_ID> \
  --role ai.languageModels.user \
  --subject serviceAccount:ajercun172vma0sg1eig
# и так для каждой роли из таблицы
```

**Подтвердить модель:** в каталоге должна быть доступна модель **Qwen3 30B-A3B**.
Нужен её точный идентификатор для URI вида `gpt://<FOLDER_ID>/qwen3-30b-a3b/latest`.
Если в каталоге она называется иначе (например, `qwen3-235b-a22b-fp8`) — сообщите точное имя.

После того как пришлёте **FOLDER_ID** (и роли выданы) — я за один проход:
проверю доступ и модель (`scripts/smoke_llm.py`), создам VM (`scripts/deploy_yc.sh`),
разверну бота и проверю сквозной сценарий.

## 6. Развёртывание

Полные шаги — в [DEPLOY.md](DEPLOY.md). Кратко:

- **Создание VM:** `FOLDER_ID=<folder> SSH_KEY=~/.ssh/id_rsa.pub bash scripts/deploy_yc.sh`
  (создаёт экономичную VM из §4.1, ставит Docker, клонирует репозиторий).
- **Запуск:** залить `.env` и `secrets/sa-key.json` на VM → `docker compose up -d --build`.
- Миграции БД и сид тестовых профилей применяются автоматически.
- Проверка модели до запуска: `docker compose run --rm bot python -m scripts.smoke_llm`.

Тестовые профили: «Профиль 1» → `12345`, «Профиль 2/3» → `ABCD`.

## 7. Секреты и безопасность

- Секреты (`.env` с `YC_API_KEY`, `secrets/sa-key.json`) **не хранятся в репозитории** (`.gitignore`).
- В рантайме на VM нужен только `.env` (Api-Key). Приватный SA-ключ нужен лишь деплой-инструментам
  (`yc` CLI) на машине разработчика — на VM его можно не держать.
- Токен бота и Api-Key передаются на VM отдельно (scp), не через git.
- Рекомендация: после настройки **перевыпустить** токен бота (@BotFather), Api-Key
  (`yc iam api-key create`) и ключ SA — они передавались в переписке. Старый Api-Key отозвать:
  `yc iam api-key delete aje5blmfp03kuc7r98ma`.
- Обработка ПДн: при первом запуске бот показывает экран согласия; данные не покидают
  российский контур (Yandex Cloud, 152-ФЗ).

**Важные нюансы окружения (для администратора):**

- Модель — `qwen3.6-35b-a3b` (лёгкая A3B текущего поколения; `qwen3-30b-a3b` под этим именем
  в каталоге нет). Это **reasoning-модель**: финальный ответ в `message.content`, цепочка
  рассуждений в `message.reasoning_content`. «Мышление» тратит ~1.5к токенов сверх ответа →
  `LLM_MAX_TOKENS` держим высоким (4000), иначе `content` приходит пустым (`finish_reason=length`).
- **AI-вызовы (LLM + SpeechKit) аутентифицируются Api-Key сервисного аккаунта.** Один ключ
  обслуживает оба сервиса (scopes `ai.languageModels` + `ai.speechkitStt`). Приватный SA-ключ
  (JWT/IAM) в рантайме больше не нужен — на VM лежит только `.env` с `YC_API_KEY`.
- AI Studio/SpeechKit принимают запросы только когда folder в URI = **домашний каталог
  сервисного аккаунта** (`b1gvtru3guuc1oipcs4p`). Каталог `project5` для AI-вызовов этим SA
  **недоступен** (ни с IAM, ни с Api-Key): «folder does not match service account folder» —
  ограничение на домашний каталог, роли его не снимают. Чтобы перенести **биллинг AI** в
  project5, нужен сервисный аккаунт, чей домашний каталог = project5 (тогда Api-Key от него).
- VM теперь в **project5** на подсети `e9bsraaf37ej054qsf8j` (квоту подсетей босс поднял,
  создал сеть+подсеть). Compute не зависит от AI-каталога, поэтому VM в project5, а AI-вызовы
  в домашний каталог SA — это нормально.
- ⚠️ **Telegram из сети YC доступен только по IPv4-адресу `149.154.167.220`** (канонический
  IP `api.telegram.org`). DNS отдаёт и другие адреса Telegram (и IPv6), которые из этой сети
  не маршрутизируются (RKN-фильтрация + нет IPv6-egress у one-to-one NAT) → бот висел и падал.
  Фикс в `docker-compose.yml`: `extra_hosts: ["api.telegram.org:149.154.167.220"]` +
  IPv4-коннектор в `app/main.py`. Если бот перестанет видеть Telegram — проверить, жив ли этот IP.
